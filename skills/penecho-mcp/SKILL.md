# PenEcho MCP

Use this skill when an external AI works through PenEcho's local MCP bridge. The
bridge can publish a bounded work surface on an explicitly enabled Canvas and
read committed user feedback for the exact session. It does not grant general
browser automation, remote transport, or access to another Canvas. Keep client
configuration and user approval within the requested scope.

## Configure only when requested

- Do not edit an MCP client configuration unless setup was explicitly requested.
  When setup is requested, inspect that client's current official MCP
  documentation/help and current configuration first; preserve unrelated
  servers and settings.
- Prefer the launch command and environment generated by PenEcho Settings/status.
  The portable fallback is `node "ABS_ROOT/src/server/mcp/stdio.js"`; the
  installed command is `penecho mcp`. Use absolute paths. Never put a dynamic
  port, local URL, token, credential, or volatile instance ID in client config.
- For an unknown client, verify its current syntax before editing it. Do not
  invent flags or silently point to another checkout. Restart only when the
  client requires it or caches its tool list.
- Configuration is separate from Canvas authorization. Ask the user to enable
  the current Canvas in PenEcho Settings → MCP service before discovery.

## Plan, preview, feedback, revise, verify, wait

Use these phases for one coherent task. Keep public updates concise and bounded.

1. **Plan.** Call `penecho_list_canvases`, select the exact connected and enabled
   `instanceId` plus `canvasId`, and call `penecho_start_session`. Use a unique
   `sessionKey` for each independent conversation and retain the returned
   `sessionId`. If more than one valid Canvas or session could be the target,
   ask one pointed question before mutating anything; title, recency, or a
   nearby connection is not a selector.
2. **Preview.** With a valid selected connection, proactively present useful UI
   choices, previews, or a visual explanation when they help the user decide or
   understand. Skip decorative progress boards or previews for routine edits.
   Publish a short plan and meaningful milestones with
   `penecho_update_session`, batching steps and events instead of streaming
   tokens or every tool call. Keep `artifactId` stable so later HTML changes
   update the same Widget.
3. **Feedback.** Before a design revision, call `penecho_read_feedback` for the
   same session. Its baseline is established only after the first session board
   is successfully applied. A presentation's `feedbackCursor` is taken after
   that presentation is applied. Keep an independent unread cursor; a later
   presentation cursor must never overwrite unread feedback.
4. **Revise.** Read the returned current screenshot when one is requested and
   extract concrete changes. Feedback pagination is spatial as well as bounded:
   distant remarks may end a page early so they remain readable. Process the
   page, then call again with `after: nextCursor` until `hasMore` is false. If
   capture or interpretation fails, retry the same `after`; do not advance the
   cursor. A vague mark does not grant consent or approval for an external,
   destructive, or irreversible action. Ask a pointed question when its target
   or intended change is unclear.
5. **Verify.** Ordinary `penecho_present_widget` calls use `capture:false`; take
   a Widget capture, or use `capture:true` to combine presentation and capture,
   only when the model needs visual evidence. Inspect reports application and
   visibility state, not painted pixels. Treat only a returned image with
   `pixelVerified:true` as pixel evidence. Keep the primary task moving if the
   bridge or capture is unavailable.
6. **Wait.** Use `status:"waiting"` when user input, approval, or a later
   feedback pass is required; use `status:"done"` only when the work is
   complete, and `error` when it cannot proceed. Poll at meaningful milestones
   or a user-authorized wait. The bridge never automatically wakes a stopped
   client and must not be polled in a tight loop.

## Exact Canvas and session contract

- Call `penecho_list_canvases` with `{}` and use only the exact returned
  `instanceId`/`canvasId`. Closed or disconnected instances and non-enabled
  Canvases are unavailable. Every later call stays on the returned
  `sessionId`.
- Start requires `instanceId`, `canvasId`, and `title` (maximum 120 characters);
  `client` and `sessionKey` are optional. Update requires `sessionId` plus at
  least one update field. Status is `working|waiting|done|error`; summary is
  at most 2,000 characters; steps are at most 24 and events at most 20.
- `penecho_present_widget` requires `sessionId`, a stable `artifactId`, `title`,
  and HTML. HTML is at most 200,000 characters and 800,000 UTF-8 bytes; width
  is 300–4096 and height is 200–4096 when supplied. Reusing an artifact ID
  upserts one preview. `capture` defaults to false; `quality` (`basic|detail`)
  is valid only with `capture:true`.
- `penecho_capture_widget` requires `sessionId` and `artifactId`, with optional
  `quality` (`basic|detail`). It captures the existing Widget on demand.
- `penecho_inspect_session` and `penecho_close_session` require `sessionId`.
  A queued update is not proof of application; use inspect for
  `render.state` (`queued|applied|accepted|error`) and application/visibility
  fields.

## Lightweight drawing and function plots

Prefer `penecho_draw` for a short visual explanation, nodes and connectors, native
text, or a bounded path. Send `sessionId`, `artifactId`, `title`, and 1–24 `items`
with stable `id` and `type` (`text|rect|ellipse|line|arrow|path`). Nodes can omit
coordinates: PenEcho lays them out. Connect nodes with `from`/`to` element IDs.
Paths use 2–256 local `{x,y}` points; line/arrow without references use two points.
Optional node `x`/`y` are local to the artifact, never world coordinates. Keep
labels short; use native `text` for longer prose. Colors are hex or transparent.

A draw call is a complete replacement of that artifact's item list: omitted
items are removed. Reuse the same element IDs to preserve object identity and
user placement; read feedback before replacing user-edited text. Do not change
a text element into a shape under the same ID. If the user removed an object,
use a new artifact ID instead of silently recreating it. Connections are resolved
when the tool runs; they are not live constraints during subsequent user drags.

`penecho_plot` takes `sessionId`, `artifactId`, `title`, `expression` (up to 180
characters), optional `xMin`/`xMax`, optional `yMin`/`yMax` with an x domain,
and optional width 300–1600 / height 200–1200. Supply expressions such as
`sin(x)` or `x^2`, not sampled points or JavaScript. Supported functions are
sin, cos, tan, sqrt, abs, exp, log and ln; constants are pi and e. Sampling,
axes and rendering run locally. Explicit parentheses clarify negated powers.

Both tools default to no screenshot. Use `capture:true` for a compressed basic
Canvas-region image in the same call when visual verification is needed. The
region includes overlapping user annotations, not an isolated object-only
raster. Capture does not consume the feedback cursor. Keep processing unread
feedback independently; never replace it with the newer presentation cursor.

Text is a native editable text object. Shapes, paths and plots are independent
native Canvas image objects: movable, resizable, saved and undoable, with MCP
source replacement in the current session. They are not iframe Widgets,
editable vector control points, or strokes in the user's eraser layer.
`penecho_capture_widget` remains limited to Widgets. For interactive UI use
`penecho_present_widget` instead.

## Read feedback contract

Call `penecho_read_feedback` with:

```json
{
  "sessionId": "<returned sessionId>",
  "after": 12,
  "limit": 20,
  "capture": true
}
```

`after` is optional and must be a non-negative integer. `limit` is 1–50 and
defaults to 20. `capture` defaults to `true`; `capture:false` is metadata-only.
The public result is compact:

```text
{sessionId, after, nextCursor, latestCursor, hasMore, truncated,
 hasFeedback, changeCount, pixelVerified, image?, width?, height?, ...}
```

It intentionally exposes no public feedback `entries`, `kind`, or text fields.
When committed changes exist and capture is enabled, the result contains one
current Canvas screenshot with nearby Canvas design and all user layers,
including text-only feedback. It is current visual context, never a historical
screenshot or OCR result. Empty reads and `capture:false` return no screenshot.

The screenshot uses the existing Canvas Agent basic capture policy: long edge at
most 1024 pixels, at most 520,000 pixels, WebP quality 0.72, and at most 700
KiB of encoded image bytes before base64 transport (which adds about one third). The runtime
automatically shrinks the raster or quality when needed to fit the limit. A
capture is one local screenshot/encoding operation; it does not call another
model, although an image returned to and read by a model can consume
image-input tokens.

Feedback retains only committed user input for this session's Canvas; draft
textarea keystrokes are absent, and input is not consumed by reading. Spatial
pagination can return fewer changes than `limit` to keep distant remarks
readable. Process the current page before advancing to `nextCursor`, and keep
reading until `hasMore:false`. If `truncated:true`, report that the retained
history is incomplete. Reading never clears Canvas dirty state or another
reader's cursor.

If a capture fails, keep the same cursor and retry after the Canvas is ready.
Do not silently switch to another Canvas or session after a disconnect. Report
the loss, require a fresh exact discovery and session, and preserve any local
work that is still valid. A disconnected or stopped client is not woken by this
workflow.

Widget controls rendered inside a preview are visual content only. Their
buttons are not callbacks to the MCP client yet; users indicate a choice in
chat or by adding a Canvas annotation. Never claim that clicking a Widget
choice automatically reaches the client.

## Skill, initialize instructions, and prompts

Installing this portable skill only adds context when the MCP client loads the
skill. Installation alone does not guarantee loading in an existing conversation;
follow the client’s skill-loading/reload behavior. It does not change client
configuration or create a callback channel. The stdio server's
`initialize.instructions` is already present and carries bridge guidance; the
MCP client controls whether it adopts, displays, or merges those instructions.
MCP prompts are user-selected templates. This server currently provides no
`prompts/list` or `prompts/get`; do not claim that PenEcho added MCP prompts or
that a prompt is automatically selected.

Canvas layout and camera behavior belong to PenEcho. Supply task identity and
stable artifact IDs; leave world placement to PenEcho and do not invent viewport tools.
New previews are automatically placed in stable task regions and rows. PenEcho
batches camera framing for newly added items, pauses following during user
interaction, and provides Show new content to resume. Updating an existing
artifact preserves its position; do not recreate it to force camera movement.
Large or distant groups remain available through the new-content action and
the session Show control rather than shrinking the entire Canvas automatically.

## Public operation and limits

Publish only safe public plans, decisions, evidence, and results. Never put
private chain-of-thought, hidden deliberation, credentials, access tokens, or
unrelated raw user data in progress fields. This local stdio bridge keeps its
dynamic ports and secrets internal. It is not Playwright, arbitrary navigation,
unrelated DOM inspection, or general computer control. Keep connection
failures and visual limitations concise while continuing the primary task.
